# Spec — refresh-token-stories-server

> Define *what* must be true when done. **No implementation details, no file
> names, no code.**

## Feature Name

Refresh-token support for the stories server.

## Business Goal

Today an expired stories access token is a dead end. The app throws the token
away, the request that failed reports an error, and stories stop working until
something else logs the user in again. The market and chat servers already solve
this: they exchange a stored refresh token for a new access token and send the
failed request again, so the user sees nothing. Stories must behave the same way,
so a user keeps browsing, posting and watching stories without being pushed back
to login.

## User Story

> As a user, I want the stories server to renew my access token by itself when it
> expires, so that my session keeps working and I never have to log in again.

## Functional Requirements

- **FR-1** — When a request to the stories server is rejected with `401`, the app
  renews the stories access token by itself. The user does nothing.
- **FR-2** — The renewal presents the stored stories refresh token and receives a
  new access token and a new refresh token. Both stored values are replaced,
  because the refresh token is single use.
- **FR-3** — After a successful renewal, the request that failed is sent again
  with the new access token. The caller receives the real answer and never sees
  the `401`.
- **FR-4** — When several stories requests are rejected at the same time, they
  share **one** renewal. When it finishes, all of them continue.
- **FR-5** — A request is renewed and replayed **at most once**. If the replay is
  rejected with `401` again, the app reports the error and does not start another
  renewal.
- **FR-6** — When the renewal cannot succeed — there is no stored stories refresh
  token, or the stored one is rejected — the app falls back to a brand-new guest
  session, the same behaviour the market and chat renewals already have. A
  verified user is not logged out; the "session expired" path that already exists
  is reused.
- **FR-7** — Every successful stories authentication stores the refresh token it
  returns, so a renewal is possible later.
- **FR-8** — The stories refresh token is stored with the same protection as the
  market and chat refresh tokens, and is cleared everywhere the session is
  cleared (logout and session reset), so a logged-out user keeps no usable token.
- **FR-9** — Renewal and replay cover **every** stories request: reads, writes,
  the seller-stories requests, and the multipart story upload. An upload body is
  rebuilt before the replay so the replayed upload carries the real file bytes.
- **FR-10** — The renewal is silent. No extra loading indicator and no message is
  shown for it. The user only sees the final result of the request they made.

## Non-Functional Requirements

- **NFR-1** — No change to what happens on a `401` from the market, marketGO,
  media, chat, wallet or comment servers. Their behaviour must stay exactly as it
  is today.
- **NFR-2** — A caller waiting for a renewal must never wait forever. The wait is
  bounded, and a renewal that never reports back releases the caller with a
  failure instead of hanging the request.
- **NFR-3** — No token value is written to logs in a release build.
- **NFR-4** — The feature adds no new user-visible text, so nothing new has to be
  translated for `ar-SY`, `en-US`, `ku-IQ` or `tr-TR`, and RTL layout is not
  affected.
- **NFR-5** — The change is reversible on its own and does not depend on any
  other ticket.

## Constraints

- The renewal must use the refresh endpoint the stories server already provides.
  No client-side workaround, and no second mechanism invented for stories — the
  behaviour follows the market and chat pattern that is already in the app.
- The baseline is the current state of the `dev_new` working tree, including the
  wait-and-replay work that is present but not yet committed. This ticket adds to
  it and does not rebuild it.
- The work touches protected runtime paths (authentication and session, the
  network layer, token storage, and generated code). It may only be changed
  inside the approved implement stage, and only where the approved plan lists it.
- Generated code is regenerated by its generator, never edited by hand.
- No backend change is requested by this ticket. The stories server already
  exposes the refresh endpoint and already returns a refresh token.

## Edge Cases

- **EC-1** — No stories refresh token is stored yet, for example on the first run
  after the app update. The renewal cannot start, so FR-6 applies.
- **EC-2** — The stored stories refresh token is itself rejected, because it
  expired or was already used. FR-6 applies.
- **EC-3** — Ten stories requests fail with `401` at the same moment. One renewal
  runs, and all ten continue after it (FR-4).
- **EC-4** — The replayed request is rejected with `401` again. The error is
  reported; no second renewal (FR-5).
- **EC-5** — The failing request is a multipart story upload. Its body can be read
  only once, so it is rebuilt before the replay (FR-9). The upload must not be
  marked as failed when the replay succeeds.
- **EC-6** — The renewal never reports a result. The waiting request is released
  with a failure after a bounded wait (NFR-2).
- **EC-7** — A stories `401` arrives while a market renewal is already running.
  The two are independent and must not block or cancel each other.
- **EC-8** — The user logs out while a renewal is running. The stored tokens are
  cleared and no renewed token survives the logout (FR-8).
- **EC-9** — The device has no network. This is not a `401`, so no renewal is
  started and the request fails as it does today.

## Out of Scope

- A silent re-login as the renewal mechanism (a real refresh endpoint is used
  instead — OQ-3).
- Refresh-token support for the wallet and comment servers. They also lack it,
  but they are separate tickets.
- Any backend change on the stories server.
- Refactoring the shared `401` handling beyond what the stories case needs.
- Adding a test framework or a test suite for the network layer.
- Any change to how the stories access token is obtained the first time (the
  existing stories login flow stays as it is, apart from storing the refresh
  token it already returns — FR-7).
- Proactive renewal before a token expires. Renewal happens only after a `401`.
