## User Story

As **a shop member inside my own shop (shop `OWNER`, or a team member holding the shop-info permissions)**,
I want to be able to **see my shop's real name, contact number, address, logo and banner in the dashboard "Edit Shop Info" screen and save my changes**,
so that **my public shop profile stays correct for buyers without asking support or using the website**.

Today `ShopInfoWidget` in `lib/features/dashBoard/presentation/pages/dashboard_page.dart` is a static mock: the three text controllers are seeded with hardcoded strings (`'Test'`, `'963937543498'`, `'sss'`), `_logoUrl` and `_bannerUrl` are always `null`, `_pickLogo()` and `_pickBanner()` are empty, and `_saveChanges()` only runs `await Future.delayed(const Duration(seconds: 1))`. This ticket replaces that mock with the two real endpoints from `.claude/docs/mobile-seller-dashboard-api-guide.md` § *Shop Info* — `GET {MARKET_API}/shop/info` (permission `READ_SHOP_INFO`) and `PUT {MARKET_API}/shop/info` (permission `UPDATE_SHOP_INFO`) — wired through the existing dashboard layers (`DashBoardEndPoints` → `DashBoardRemoteDataSource` → `DashBoardRepository` → use case → `DashboardBloc`), the same path the gallery feature already uses. **In scope:** reading the record, showing the five editable fields, the logo/banner picker and its upload to the media-server folder `seller`, and the full-body `PUT`. **Out of scope:** currency editing, product-approval standing, boutique banners, shop locations, the shop switcher itself, and every Orders screen — the guide states those belong to other screens and endpoints. Related local work item: `_specs/dashboard-gallery-page` (⚠️ no ClickUp id), which introduced the media-upload and dashboard-bloc patterns to reuse.

# Acceptance Criteria

## Scope & Tenant Safety

1. Every `GET /shop/info` and `PUT /shop/info` request sends `Authorization: Bearer <MARKET_TOKEN>` **and** `X-Seller-ID: <sellerId>` for the shop currently selected in the dashboard, plus the `country` and `lang` headers, as `.claude/docs/mobile-seller-dashboard-api-guide.md` § *Auth quick reference* requires.
2. The `sellerId` sent is always the shop the user is currently viewing; the widget never sends a shop id typed by the user, cached from another screen, or left over from a previously selected shop.
3. When the selected shop changes, the screen clears the loaded record and refetches. Data from the previous shop is never displayed under the new shop and never re-saved under the new shop id.
4. No shop-info field is written to any global or cross-shop cache. The loaded record lives in the dashboard state for the selected shop only.
5. The screen writes only the five fields `name`, `address`, `contact`, `image`, `banner`. No request from this screen changes currency, approval standing, boutique banners, or shop locations.

## Authorization

1. Before calling `GET /shop/info`, the app reads the permission list already loaded from `GET {MARKET_API}/shop/auth/permissions`. A control is allowed when `permissions.includes(<PERM>) || permissions.includes("SUPER_ADMIN")`.
2. When the permission list loaded successfully and contains neither `READ_SHOP_INFO` nor `SUPER_ADMIN`, the app **does not send the request at all**. It shows a "you do not have permission to view shop info" message with **no spinner and no retry button**, because a retry cannot succeed.
3. When the permission list itself failed to load (the state is *unknown*, not *denied*), the app **does send** `GET /shop/info` and lets the backend decide. An unknown permission state never locks out a seller who really has access.
4. "Save Changes", the logo "Change" button, and "Change Banner" are hidden (or disabled with a stated reason) when the permission list loaded successfully and contains neither `UPDATE_SHOP_INFO` nor `SUPER_ADMIN`.
5. Client-side gating is UX only. A `403`, or a `success: false` permission message from the backend, is still handled and shown. The app never treats client gating as proof of access.

## General Behavior

1. Opening the "Edit Shop Info" tab triggers exactly one `GET {MARKET_API}/shop/info` call and shows a loading state until it resolves.
2. The response body is read tolerantly as `res.data ?? res`. Every field is read defensively; a missing or `null` field never throws and never breaks the screen.
3. On success the form is prefilled from the response: `name` → Shop Name, `contact` → Contact, `address` → Address, `image` → the logo box, `banner` → the banner box. The hardcoded values `'Test'`, `'963937543498'` and `'sss'` are removed from the widget.
4. Display URLs for `image` and `banner` are built the way the web client builds them: if the stored value contains `http`, it is used as is; otherwise it is prefixed with `{MEDIA_IMG}` with exactly one `/` between the two parts. A bare filename, a relative path, and a full URL all render.
5. `currency: { code, name }` from the same response is stored in the dashboard state so the other dashboard screens (product form, product list) can show the shop's currency. This screen does not display or edit it.
6. `is_new_products_approval` from the same response is stored in the dashboard state with this rule: **missing or `null` means "not gated" (treat as `true`)**; only an explicit false-y value (`false`, `0`, `"false"`, `"0"`) means the seller is restricted. "Absent" is never treated as "blocked".
7. A failed `GET` — a transport error, or a body carrying `success: false` — shows the returned `message` and a retry action. The form stays empty and no partial record is shown.
8. Tapping the logo "Change" or "Change Banner" opens the image picker, lets the user crop, then uploads the file to the media server with folder `seller`: first `POST {MEDIA}/gated/ticket` with `Authorization: Bearer <MARKET_TOKEN>` and body `{ folder, story, count }`, then the upload with **both** `x-api-key: {MEDIA_KEY}` and `X-Upload-Ticket: <ticket>`. A fresh ticket is taken for every upload.
9. A picked image is shown in its box right after a successful upload and before saving. The picked value is persisted only when the user presses "Save Changes".
10. A failed upload shows the error, leaves the previously shown image in place, and does not change the value that would be sent on save.
11. The two paths are added to `DashBoardEndPoints` in `lib/common/constant/configuration/dashBoard_url_routes.dart` through the existing `shopScope()` extension, and the calls run through `DashBoardRemoteDataSource` → `DashBoardRepository` → use case → `DashboardBloc`, matching the gallery feature. The widget itself makes no HTTP call.

## Form Fields

### Required Fields

1. **Shop Name** (`name`) — text
2. **Contact** (`contact`) — phone digits, country code first (example: `971…`)
3. **Address** (`address`) — multi-line text

Rules:

1. All three required fields are validated before any request is sent.
2. When validation fails, no `PUT` request is sent and the failing field shows its own message.

### Optional Fields

1. **Shop Logo** (`image`) — square image
2. **Shop Banner** (`banner`) — wide image, ratio 6:1

## Behavior After Saving

1. "Save Changes" sends `PUT {MARKET_API}/shop/info` with **all five fields every time**: `{ name, address, contact, image, banner }`. There is no partial update.
2. `image` and `banner` are sent as a **bare filename**: only the part after the last `/` is kept, so `/seller/1781080470388204.png` is sent as `1781080470388204.png`.
3. When the user picked no new file, the **existing** value from the `GET` is re-sent, flattened to a bare filename in the same way.
4. When there is no image at all, `null` is sent for that field.
5. While the request is in flight the button shows its saving state and is disabled; a second tap cannot start a second request.
6. On a response with `success: true`, a success message is shown, the in-memory record is updated with the values just saved, and the form keeps showing those values.
7. On a response with `success: false` (including a `200` that carries it) or a transport error, the returned `message` is shown, the form keeps the user's edits, and nothing is discarded silently.
8. A known limit is written as a code comment: this filename round-trip holds only while shop media stays in the single `seller` folder. If the backend ever returns a value from another folder, the folder is lost on the next save. That case is untested and is not fixed by this ticket.

## Validation & Constraints

1. `name`, `contact` and `address` must not be empty after trimming.
2. `contact` must match `^\+?\d+$`. There is no length check and no real country-code check — the "971…" hint is guidance under the field, not a rule.
3. Client-side validation is deliberately the same as the web client's and is known to be weak. The backend's own rules (max lengths, phone format, whether `image` may be `null`) are **not verified**; whatever `message` the backend returns is shown to the user as it is.
4. Success is decided by the `success` flag in the `{ success, message, data }` envelope, **not** by the HTTP status alone.
5. The logo and banner pickers accept image files only.

## UI & API Consistency

1. The three required fields and the `^\+?\d+$` contact rule are enforced in the UI exactly as stated above; anything the backend rejects on top of that is surfaced from its `message`.
2. UI gating (`READ_SHOP_INFO` to read, `UPDATE_SHOP_INFO` to save) matches the permissions the backend enforces on the two endpoints.
3. API errors are surfaced from the structured envelope (`success`, `message`) and not from raw exception text: a `403` shows a permission message, a `422` or `400` shows the backend `message`.
4. Loading, empty, error and permission-denied are four distinct states on screen. A permission denial never renders as an endless spinner.

## Audit & Logging

1. On a successful save, one app log line records the shop id, which of the five fields changed, and the result — never the full record and never any token.
2. On a failed `GET`, `PUT`, ticket request, or upload, the failure is reported to Sentry with the endpoint, the HTTP status, the `success` flag and the `message`.
3. `MARKET_TOKEN`, `{MEDIA_KEY}` and `X-Upload-Ticket` values are never written to logs or to Sentry.
4. A permission-denied skip (Authorization criterion 2, where the request was never sent) is logged locally as a skip, not as an error.

# Test Cases

## Happy Path — Load the shop profile and save an edited name

**Given** I am signed in as a shop `OWNER` whose permission list contains `READ_SHOP_INFO` and `UPDATE_SHOP_INFO`
**And** the backend holds `name: "My Shop"`, `contact: "971500000000"`, `address: "Dubai"`, `image: "/seller/logo1.png"`, `banner: "/seller/banner1.png"` for my shop
**When** I open the "Edit Shop Info" tab, change Shop Name to "My New Shop", and press "Save Changes"
**Then**
- One `GET {MARKET_API}/shop/info` was sent with `X-Seller-ID` = my shop id, plus `country` and `lang`
- The form showed "My Shop", "971500000000" and "Dubai", and the two image boxes rendered from `{MEDIA_IMG}/seller/logo1.png` and `{MEDIA_IMG}/seller/banner1.png`
- One `PUT {MARKET_API}/shop/info` was sent with body `{ name: "My New Shop", address: "Dubai", contact: "971500000000", image: "logo1.png", banner: "banner1.png" }`
- The button was disabled while the request was in flight
- A success message is shown and the form still displays "My New Shop"

---

## Happy Path — Replace the logo and save

**Given** I hold `UPDATE_SHOP_INFO` and the screen is loaded with `image: "/seller/old.png"`
**When** I press "Change", pick and crop an image, and press "Save Changes"
**Then**
- A fresh `POST {MEDIA}/gated/ticket` was sent with the market token and body `{ folder: "seller", story: false, count: 1 }`
- The upload was sent with both `x-api-key` and `X-Upload-Ticket`, folder `seller`
- The new image appeared in the logo box before saving
- The `PUT` body carried the **bare filename** returned by the upload (for example `1781080470388204.png`), and `banner` carried the existing banner flattened to a bare filename

## Happy Path — A full URL and a bare filename both render

**Given** the backend returns `image: "https://cdn.example.com/a/logo.png"` and `banner: "banner9.png"`
**When** the screen loads
**Then**
- The logo is displayed from `https://cdn.example.com/a/logo.png` unchanged, because the value contains `http`
- The banner is displayed from `{MEDIA_IMG}/banner9.png` with exactly one `/` between the base and the filename
- Neither value raises an exception

**When** the screen loads
**Then**
- `AED` is available in the dashboard state for the product screens
- `is_new_products_approval` is treated as `true` ("not gated"), because the field is missing
- The "Edit Shop Info" screen shows no currency control and no approval control

## Validation Error — Empty required field

**Given** the screen is loaded with a valid record
**When** I clear the Address field and press "Save Changes"
**Then**
- A validation message is shown on the Address field
- **No** `PUT {MARKET_API}/shop/info` request is sent
- Nothing is saved and my other edits stay in the form

---

## Validation Error — Contact is not a valid number

**Given** the screen is loaded with a valid record
**When** I type `+971-50-000` into Contact and press "Save Changes"
**Then**
- A validation message is shown, because the value does not match `^\+?\d+$`
- **No** `PUT` request is sent
- Typing `971500000` clears the message and the save can then proceed

---

## Validation Error — Backend rejects the value inside an HTTP 200

**Given** the screen is loaded and my input passes client validation
**When** I press "Save Changes" and the backend replies HTTP `200` with `{ success: false, message: "Shop name is too long" }`
**Then**
- "Shop name is too long" is shown to the user
- The save is treated as **failed**, not as success, because `success` is `false`
- My edits stay in the form and are not overwritten

---

## Authorization Failure — No `READ_SHOP_INFO`

**Given** my permission list loaded successfully and contains neither `READ_SHOP_INFO` nor `SUPER_ADMIN`
**When** I open the "Edit Shop Info" tab
**Then**
- **No** `GET {MARKET_API}/shop/info` request is sent
- A "no permission" message is shown, with no spinner and no retry button
- The form fields and the Save button are not usable

---

## Authorization Failure — No `UPDATE_SHOP_INFO`

**Given** my permission list contains `READ_SHOP_INFO` but neither `UPDATE_SHOP_INFO` nor `SUPER_ADMIN`
**When** I open the "Edit Shop Info" tab
**Then**
- The record loads and is displayed read-only
- "Save Changes", the logo "Change" button and "Change Banner" are hidden (or disabled with a stated reason)
- If a `PUT` is still reached, the API returns `403` and its `message` is shown

---

## Authorization Failure — Permission list unknown

**Given** the call to `GET {MARKET_API}/shop/auth/permissions` failed, so my permissions are unknown rather than denied
**When** I open the "Edit Shop Info" tab
**Then**
- The `GET {MARKET_API}/shop/info` request **is** sent and the backend decides
- If it succeeds, the record is shown normally
- If it returns `403`, the permission message is shown and I am not locked out by the client

---

## Tenant Safety — Switching shops does not leak data

**Given** I manage shop A and shop B, and the "Edit Shop Info" screen is loaded with shop A's record
**When** I switch the dashboard to shop B
**Then**
- The form clears and a new `GET {MARKET_API}/shop/info` is sent with `X-Seller-ID` = shop B's id
- Shop A's name, contact, address, logo and banner are never displayed under shop B
- Pressing "Save Changes" after the switch sends shop B's id and shop B's values only
