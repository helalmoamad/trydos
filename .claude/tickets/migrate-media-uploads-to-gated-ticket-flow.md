## User Story

As **a Buyer or Seller uploading media (story, chat attachment, profile photo, order
rating or return-request image)**,
I want to be able to **have every file uploaded through the media server's gated,
ticket-authorized flow**,
so that **uploads are authorized against my own session, size limits are enforced
before any network transfer, and no file bypasses the media service**.

The media service replaced its open upload endpoint with a **two-step gated flow**: the
client first mints a short-lived, single-use ticket (`POST /gated/ticket`) using the
user's access token, then performs the upload with that ticket in the
`X-Upload-Ticket` header. This ticket carries the `folder`, `count` and `story`
settings, which the upload request itself can no longer override. **In scope:** every
existing file upload in the app — user story, seller story, chat attachments, profile
photo, order-rating images, return-request images — plus 401 handling and the chat
attachment size limit. **Out of scope:** image search (`webApp`, analysis only, nothing
stored), Cloudinary (all call sites already disabled), and the bulk/Excel endpoints,
which are wired at the network layer but intentionally left uncalled until a feature
needs them.

# Acceptance Criteria

## Session & Account Safety

1. The ticket request `POST /gated/ticket` sends the authenticated user's market access
   token as `Authorization: Bearer <token>`; no upload is possible without a valid
   session.
2. Every ticket is single-use with a 120-second TTL and is minted immediately before its
   upload; a ticket is never reused across two uploads.
3. Upload requests carry only `X-Upload-Ticket`; the market, chat, stories and wallet
   tokens are never sent to the media server.
4. The uploaded file is stored under the folder bound to the ticket, so one user's media
   can never be written into another module's or another user's folder by tampering with
   the upload body.

## Authorization

1. Only an authenticated user may mint a ticket; the media service rejects an unauthenticated
   request with `401`.
2. A `401` from any media-server request triggers the app's market token refresh flow
   (`RefreshTokenEvent`), matching the behaviour already applied to market-scoped servers.
3. A missing, expired or already-spent ticket causes the upload to return `403`, which is
   surfaced to the user as a failed operation — never as a silent success.
4. Uploads exceeding the ticket's `max_bytes` are rejected by the service with `413`.

## General Behavior

1. Six upload paths use the gated flow: user story, seller story, chat attachment,
   profile photo, order-rating image, return-request image.
2. Single-file uploads use `POST /gated/upload`; chat attachments use
   `POST /gated/chat/upload_file`.
3. The `folder` bound to each ticket is: `stories` (seller story), `customers/profile`
   (profile photo), `rating_orders` (order rating), `return_request_products` (return
   request). User stories mint with `story: true` and no folder; chat attachments are
   stored by the service under `chat/`.
4. Leading and trailing `/` characters are stripped from any `folder` value before it is
   sent, satisfying the service's folder validation rules.
5. Upload requests never set `Content-Type` manually; the HTTP client sets
   `multipart/form-data` with its own boundary.
6. Upload request bodies contain only the `file` part; `folder`, `custom_file_path` and
   `file_name` are no longer sent, because the ticket is authoritative.
7. No file upload in the app targets the market server or the chat server any more.

## Form Fields

### Required Fields

1. **file** — the binary part of every upload request.
2. **Authorization** — Bearer access token on the ticket request.
3. **X-Upload-Ticket** — ticket string on every upload request.

Rules:

1. All three are present before a request is issued; a missing ticket aborts the upload
   locally and returns a failure without a network call.

### Optional Fields

1. `folder` — ticket request only.
2. `count` — ticket request only, defaults to `1`, maximum `50`.
3. `story` — ticket request only, defaults to `false`; `true` lowers the size limit to
   10 MB.

## Behavior After Saving

1. A successful single upload returns `key`, `size`, `type` and `url`; video uploads also
   return `durationSeconds` and `variants`, and story uploads additionally return `story`.
2. The relative sub-path is derived from the returned `url` by removing the delivery
   prefix (`/image/upload/`, `/video/upload/`, …) and is passed to the market API in the
   same position the previous `sub_path` occupied, so stored links keep their existing
   shape.
3. A successful chat upload returns the `{ isSuccessful, data: { file_path, … } }`
   envelope, and `file_path` is sent unchanged as the message's media content.
4. On failure the calling BLoC marks the message or operation as failed; no partial
   record is persisted.

## Validation & Constraints

1. Chat attachments larger than **25 MB** are rejected **before** upload begins, in the
   single choke point every attachment path passes through, and no temporary message is
   created.
2. The rejection shows the localization key `chat_attachment_size_limit`.
3. Story uploads are capped at 10 MB and standard uploads at 100 MB by the ticket's
   `max_bytes`.
4. File type and stored extension are determined by the service from the file's leading
   bytes; the client's declared content type is advisory only.

## UI & API Consistency

1. Every upload failure — expired token, spent ticket, oversized file, network error —
   results in a visible failed state on the affected message or screen.
2. A failed chat image shows a retry control and a failure marker, identical to the
   existing behaviour for video, voice, document and text messages.
3. Tapping retry re-runs the full flow, minting a new ticket, since tickets are
   single-use.

## Localization & RTL

1. The new key `chat_attachment_size_limit` exists in all four bundles
   (`en-US`, `ar-SY`, `ku-IQ`, `tr-TR`) and in `lib/generated/locale_keys.g.dart`.
2. No hard-coded user-visible string is introduced by this change.
3. The retry control on a failed chat image renders correctly in both RTL and LTR.

## Audit & Logging

1. A rejected access token logs "Access token rejected — requesting a token refresh…" in
   debug builds before dispatching the refresh.
2. Upload failures propagate the original `Failure` (including the HTTP status code) to
   the calling BLoC rather than being replaced by a generic error.
3. No access token, ticket string, or file bytes are written to logs.

# Test Cases

## Happy Path — Send a chat image through the gated flow

**Given** a signed-in Buyer with a valid access token
**And** an image smaller than 25 MB selected in a chat
**When** the Buyer sends the image
**Then**
- `POST /gated/ticket` is called once with `Authorization: Bearer …` and `count: 1`
- `POST /gated/chat/upload_file` is called with `X-Upload-Ticket` and a single `file` part
- the message is sent with the returned `file_path` and appears as delivered
- no request is made to the chat server's `upload_file` endpoint

---

## Happy Path — Upload a profile photo and keep the stored link shape

**Given** a signed-in Buyer on the profile screen
**When** the Buyer selects a new profile photo
**Then**
- the ticket is minted with `folder: "customers/profile"`
- the file is uploaded to `POST /gated/upload`
- the market API receives the sub-path `customers/profile/<file>` — without the
  `/image/upload/` prefix
- the profile photo renders from the same URL shape used before this change

---

## Validation Error — Reject an oversized chat attachment

**Given** a signed-in Buyer in a chat
**When** the Buyer selects a file larger than 25 MB
**Then**
- the message `chat_attachment_size_limit` is displayed
- no ticket is minted and no upload request is issued
- no pending message is added to the conversation

---

## Authorization Failure — Expired access token during upload

**Given** a Buyer whose market access token has expired
**When** the Buyer sends a chat image
**Then**
- `POST /gated/ticket` returns `401`
- the app dispatches its token refresh flow
- the message is marked as failed and shows the retry control with the failure marker
- tapping retry mints a **new** ticket and completes the upload after the token is refreshed

---

## Authorization Failure — Spent or expired ticket

**Given** a ticket that was already consumed by a previous attempt
**When** the client attempts an upload with that ticket
**Then**
- the service returns `403`
- the operation is reported as failed to the user
- the next attempt mints a fresh ticket rather than reusing the spent one
