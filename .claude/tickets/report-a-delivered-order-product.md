## User Story

As **a Buyer who has received an order**,
I want to be able to **report what went wrong with a delivered product — its quality,
the delivery time, the delivery worker, or the delivery vehicle — and optionally attach
a note and one photo**,
so that **the store learns about real delivery and quality problems and can act on them**.

The "Report This Product" action already existed in the order-details actions sheet but
had no behaviour behind it. This ticket makes it functional: a bottom-sheet panel with
four groups of multi-select chips, an optional note, and one optional photo, submitted to
`POST /customer/order/report`. **In scope:** the report panel, its validation, the submit
call in both payload shapes, the once-per-product rule and the post-report card state, and
the delivered-only gate. **Out of scope:** reporting a whole order (the report is always
scoped to one product), editing or withdrawing a submitted report, any seller-side or
admin-side view of reports, and multi-photo attachments.

# Acceptance Criteria

## Session & Account Safety

1. The report request is authenticated with the Buyer's market token, so a Buyer can only
   report products inside their own orders.
2. `order_id`, `order_detail_id`, `product_id` and `order_group_id` are taken from the
   order the Buyer is currently viewing; they are never entered manually or guessed.
3. No other backend's token is sent with the report request.

## Authorization

1. The report action is visible only for orders whose status is `delivered` or a
   `return`-family status; it is not rendered for pending, preparing, shipped or
   cancelled orders.
2. A product may be reported **once**. After a successful report the card is rendered
   without any tap action.
3. Unauthorized or rejected requests surface the backend error message to the Buyer and
   leave the product reportable.

## General Behavior

1. Tapping "Report This Product" opens a bottom-sheet panel titled with
   `report_this_product` and the subtitle `report_this_product_subtitle`.
2. The panel shows four groups in this order: **Product Quality** (`product_quality`),
   **Delivery Time** (`delivery_time`), **Delivery Worker** (`delivery_worker`),
   **Delivery Car** (`delivery_car`).
3. Each group's options are rendered as chips; multiple chips may be selected within a
   group and across groups.
4. Tapping a selected chip deselects it.
5. A selected chip is visually distinct from an unselected one.
6. "Cancel" closes the panel and discards the draft; nothing is sent.

## Form Fields

### Required Fields

1. **At least one option** from any of the four groups.

Rules:

1. The Submit button is disabled and rendered in its disabled colour until at least one
   option is selected.
2. Deselecting the last remaining option disables the Submit button again.

### Optional Fields

1. **Additional notes** — free text, labelled with `report_optional`.
2. **Photo** — exactly one image, labelled with `report_optional`; the picker offers
   gallery and camera, matching the rating and return flows.

Rules:

1. Once an image is chosen, the "Add a photo" box is replaced by its preview with a
   remove control.
2. Removing the image restores the "Add a photo" box.
3. A second image cannot be attached.

## Behavior After Saving

1. On success the panel closes automatically.
2. The product's card immediately shows `report_received_title` as its title and
   `report_received_body` as its body, and stops responding to taps — with no page reload
   or refetch.
3. A success message is shown via the app's existing message helper, using the backend
   message when present and `report_received_title` otherwise.
4. On failure the panel stays open with the Buyer's selections intact, and the backend
   error message is shown.
5. The reported state also survives a page refresh, because the backend returns
   `is_reported` on the order detail.

## Validation & Constraints

1. The request body is **JSON** when no photo is attached and **`multipart/form-data`**
   when one is.
2. `points` is an array of `{ point, values[] }`; in the multipart form it is serialised
   as `points[i][point]` and repeated `points[i][values][]` entries.
3. Only these option values are ever sent: `damaged`, `not_as_described`,
   `poor_material`, `wrong_item`, `expired`, `too_late`, `missed_window`, `no_eta`,
   `faster_than_expected`, `rude`, `unprofessional`, `no_show`, `asked_extra_fee`,
   `polite`, `dirty_vehicle`, `no_cooling`, `unsafe_handling`, `no_vehicle`.
4. The note is trimmed before sending; an empty note is sent as an empty string.
5. While the request is in flight the Submit button shows a loader and cannot be tapped
   again, so no duplicate report is created.

## UI & API Consistency

1. The "at least one option" rule is enforced in the UI by disabling Submit, and the API
   remains the authority on the once-per-product rule via `is_reported`.
2. Opening the keyboard for the notes field does not hide it: the list's bottom padding
   follows the keyboard inset and the field is scrolled into view.
3. The panel scrolls so that the notes field, photo box, Submit and Cancel are all
   reachable on small screens.

## Localization & RTL

1. Thirty localization keys prefixed `report_` exist in **all four** bundles
   (`en-US`, `ar-SY`, `ku-IQ`, `tr-TR`) and in `lib/generated/locale_keys.g.dart`.
2. No user-visible string in the panel or the card is hard-coded.
3. Chips, group titles, the notes field and the photo box render correctly in RTL
   (Arabic/Kurdish) and LTR (English/Turkish).

## Audit & Logging

1. A failed report logs the returned `Failure` with its HTTP status code through the
   existing error pipeline.
2. Selected option keys, the note and the image are sent only to
   `POST /customer/order/report`; none of them are written to logs.

# Test Cases

## Happy Path — Report a delivered product with note and photo

**Given** a Buyer viewing a delivered order
**And** the product has not been reported before
**When** the Buyer opens "Report This Product", selects "Damaged" and "Arrived too late",
writes a note, attaches one photo and taps Submit
**Then**
- the request is sent as `multipart/form-data` with `points[0][point]`,
  `points[0][values][]`, `note` and `image`
- the panel closes and a success message is shown
- the card now reads "We received your report" / "Thanks for your thoughts" and no longer
  responds to taps

---

## Happy Path — Report with selections only

**Given** a Buyer viewing a delivered order
**When** the Buyer selects one chip and taps Submit without a note or photo
**Then**
- the request is sent as **JSON** containing `order_id`, `order_detail_id`, `product_id`,
  `order_group_id`, `points` and an empty `note`
- the report is accepted and the card switches to its reported state

---

## Validation Error — Submit with no option selected

**Given** the report panel is open with nothing selected
**When** the Buyer looks at the Submit button
**Then**
- the button is disabled and rendered in its disabled colour
- tapping it sends no request
- selecting one chip enables it, and deselecting that chip disables it again

---

## Authorization Failure — Product already reported

**Given** a product whose order detail returns `is_reported: true`
**When** the Buyer opens the order actions sheet
**Then**
- the card shows "We received your report" / "Thanks for your thoughts"
- tapping the card does nothing and the panel does not open

---

## Authorization Failure — Order not delivered

**Given** an order whose status is `pending`, `preparing`, `shipped` or `canceled`
**When** the Buyer opens the order actions sheet
**Then**
- the "Report This Product" card is not rendered at all
- no spacing gap is left where the card would have been

## Implementation Notes *(for the reviewer — not part of the ClickUp description)*

**Added**

- `lib/features/home/domain/use_cases/report_order_product_usecase.dart` — builds the JSON
  or multipart body; `points[i][point]` / `points[i][values][]` are appended field by field
  because `FormData.fromMap` cannot express nested indices
- `lib/features/home/presentation/widgets/order_report_panel.dart` — the whole panel, kept
  out of the 11k-line order-details page
- `MarketEndPoints.reportOrderProductEP` → `POST /customer/order/report`
- `OrderListDetailModel.isReported`, parsed from `is_reported` as `true` / `1` / `"1"`
- `ReportOrderProductStatus`, `ReportOrderProductEvent`,
  `ResetReportOrderProductStatusEvent` and their handlers in `OrderBloc`
- 30 `report_*` keys in the four bundles and in `locale_keys.g.dart`

**Changed**

- `order_details2_page.dart` — `panelReportContent`, the `"Report_This_Product"` branch,
  the `_canReportOrder` gate, and the reported/unreported card states

**Design decisions worth reviewing**

- The card reads the page's **local** `order` copy, so a successful report marks the detail
  locally through an explicit `onReported` callback (separate from `onClose`, which also
  fires on Cancel). `OrderBloc` additionally marks the detail inside `getOrdersModel` so
  other screens reading bloc state stay consistent.
- `_canReportOrder` treats `return`-family statuses as delivered, matching the rule the
  page already uses for its delivered icon.
- The photo is uploaded **inline to the market server**, per the agreed spec. This is the
  only remaining upload in the app that does not go through the gated media flow — see
  *Migrate Media Uploads to Gated Ticket Flow*.

**Open question for the backend**

- `is_reported` is assumed to be returned on the **order detail** (`details[i]`), not on
  the order. Confirm before release.

**Verification** — `flutter analyze` reports `No issues found` for the whole project;
`dart run build_runner build --delete-conflicting-outputs` was re-run for the new
injectable use case.
